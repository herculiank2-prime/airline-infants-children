**Summary.** The design is well above average. It has one integration numbering scheme, real options in the ADRs, a server-rendered fragment-driven accordion, a clear data-layer contract, and a thoughtful PII story for the Joey Club enquiry. Three problems would cost marks directly against acceptance criteria:

- The "≤ 5 minutes" freshness promise (A-02 / SD-08) can't be met with the cache headers as designed. The CDN, Dispatcher, stale-while-revalidate and browser lifetimes add up, and the immutable vhost unsets `Age`.
- The persisted query (HD-02) can't return "the same items" as the Java selection logic, because folder, tag, limit and filter semantics differ.
- SD-03's rendered images don't exist, so `SOLUTION_DESIGN.md` embeds broken links.

Beyond those, the design misses several AEMaaCS-specific realities: the Preview tier, FileVault filter modes for `/conf`, CDN-as-code ownership, production URL mapping, and the fact that the Dispatcher validator can run without Docker. The delivery plan also wouldn't survive contact with a real team.

## Extended reasoning — Blockers and Majors

### AR-01 — Cache freshness bound (Blocker)

Content passes through four caches, and each one starts its own clock. On AEMaaCS, the immutable vhost does `Header unset Age` when default caching is on. So the Adobe CDN can't tell that a Dispatcher-served file is already 59 s old, and it caches it for its full `s-maxage`. `stale-while-revalidate=300` then lets the CDN serve that object for up to another 300 s while it refetches in the background. On a low-traffic page, the first visitor after expiry still gets stale content. Add the browser's own `max-age=60` and a legal change can be invisible to a returning visitor for about 12 minutes. A-02, OQ-09 and ADR-004 all promise 5.

There's also an internal contradiction about which TTL Dispatcher uses. The documents say 300 s, but the header sent gives Dispatcher 60 s. Either fix the numbers, or explain the Dispatcher version's `s-maxage` behaviour and test it. Splitting `Cache-Control` (browser and Dispatcher) from `Surrogate-Control` (CDN) is the cleanest way to give each layer an explicit budget. Put the formula in SD-08 so a reviewer can check it.

### AR-02 — Persisted query parity (Blocker)

HD-02's acceptance criterion is literal: the persisted query "returns the same items". The Java service was designed for authoring flexibility (hierarchical tags, any/all matching, asset tags, direct children, blank-item filtering). Each of those features is something the GraphQL query either can't express or expresses differently. The fix is to let GraphQL's capabilities limit the Java semantics, not the other way round. Then prove parity with one test that runs both against the same fixture. This also protects SE-01, because the JSON-LD comes from the Java path.

### AR-03 — Rendered diagrams (Blocker)

SD-03 is pass/fail on "committed source **with a rendered image**". Today the client-facing document shows three broken images, and its header refers to a script that doesn't exist. This is cheap to fix but would be marked down immediately.

### AR-04 — Dispatcher validation is possible locally (Major)

The analysis treats "no Docker" as "no validator". The Windows Dispatcher tools in the SDK distribution include the validator binary. Running it closes most of R-02 and gives DP-01 real evidence. Committing the `enabled_*` entries as Git symlinks keeps Linux tooling and Cloud Manager behaving as Adobe intends, while Windows developers still get readable files.

### AR-05 — FileVault filter modes (Major)

This is the most common AEMaaCS packaging defect. With `merge`, a policy change committed in sprint 2, such as adding a component to the allowed list, installs fine on a clean SDK but never reaches an environment that already has the node. PT-01 and the "design drives build" principle both depend on templates and policies being code-owned (`update`), while author-edited content stays `merge`. The current DAM exclude rule would also make EN-02's "including the sample page and fragments" fail outright.

### AR-06 — NZ rollout coherence (Major)

SD-10 asks how the design supports NZ *and what changing it would cost later*. As written, AU folder mode plus NZ-tagged fragments in the same folder leaks NZ rules onto the AU page. That's a legal-content defect, not just a cosmetic one. The design needs one selection model for both markets and an override rule for market variants of the same question.

### AR-07 — Persisted query delivery (Major)

Adobe deliberately bypasses Dispatcher for persisted queries by default, to protect `;`-encoded variables. Turning caching on removes that safeguard. The design must show that parameterised URLs are cached and served correctly, and that CORS (if a browser-based consumer exists) works through a cached Dispatcher response. AEM's default persisted-query cache headers are much longer than the HTML budget, so leaving them in place reintroduces AR-01 for the app.

### AR-08 — Traversal bound (Major)

Three documents give three different limits in two different units. A silent cap with depth-first order makes the result depend on the repository structure, which is the opposite of the "same fragments everywhere" promise. Either make the bound explicit and visible to authors, or use the indexed query pattern Core already uses for Content Fragment List.

### AR-09 / AR-10 — Preview tier and local publish (Major)

The client "already runs AEMaaCS", which includes a Preview service. Legal review of infant rules on a preview URL is the platform-native answer to "Legal reviews any change", and it gives PF-01's "preview mode" a concrete meaning. Locally, the publish instance is installed but unused. Every publish-only claim in the design (the cache filter, anonymous DAM and CF reads, blocked selectors) can be checked on 4503 without Docker.

### AR-11 — Hero image budget (Major)

The NFR is a 640w budget, but the browser will choose the 1280w file on the emulated device used to measure PF-01, and may choose the original on desktop. Either the budget or the `srcset` must change. ADR-007 should also be honest that rejecting Core Image and web-optimised delivery has a production page-weight cost, not just a local-SDK limitation.

### AR-12 — CDN ownership (Major)

SD-04 wants every element coded against the current state. Three designed features (rate limiting, purge, HSTS) need CDN configuration through Cloud Manager's config pipeline, so the CDN is "changed". The security-header table must say which layer sets each header, or the build will set some twice and others not at all.

### AR-13 — Delivery plan (Major)

"A delivery plan someone could run" means it must include the work a real team does beyond writing components: QA, the accessibility audit, legal copy, Tags rules, environment and CDN setup, and contingency. It also has to match the team of five described in SD-14.

### AR-14 — URLs and crawlers (Major)

Canonical, hreflang, sitemap, Dispatcher filters and invalidation paths all depend on the public URL shape. Nothing in the design defines it. Crawlers are a required actor in SD-02, and an explicit AI-crawler policy is a client decision that should be in the open-questions register.

### AR-15 — Targeted invalidation (Major)

I-13 is "designed only", but SD-06 and SD-09 are assessed on whether the design is sound. A surrogate-key purge needs a surrogate key on the response. A reference lookup over component nodes needs an index. An author-side event handler needs at-least-once processing (a Sling Job). All three are missing.

## What is good

- **One integration numbering scheme** (I-01..I-14), reused across the diagrams, registers and ADRs, with diagram sources synced into `02-design.md` by script. The `.mmd` files and the inline blocks were checked and match exactly.
- **Real ADR trade-offs**: ADR-004 rejects `statfileslevel` flushing and client-side fetching for the right reasons; ADR-005 rejects Sling Jobs because they'd store PII at rest; ADR-015 drops the broad default filters.
- **The server-rendered accordion** follows the WAI-ARIA pattern, uses native `<button>` (no custom key handling) and renders the collapsed state on the server (no CLS). The data-layer contract is namespaced and testable.
- **The Joey Club design** keeps PII out of the JCR, logs, caches and analytics; uses Cloud Manager secret variables through `$[secret:…]`; and has bounded retries and alerting.
- **The analysis is honest about the environment** (archetype patch, SDK API pinning, a noisy shared instance, no Docker), and the departures are recorded as ADRs rather than hidden.
- **Using a Sling filter to drive `enableTTL`** is a correct, non-obvious AEMaaCS technique: `mod_headers` values aren't visible to the Dispatcher TTL logic. It just needs the scoping and numbers fixed (AR-01, AR-23).
